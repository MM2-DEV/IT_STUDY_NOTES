## Relational Model {#relational-model}

### Definition of Relational Model

The relational model is a data model in which **data and relationships are represented as a collection of tables (relations)** linked by common key values.

Each table has rows (tuples) and columns (attributes). It was proposed by **E. F. Codd** of IBM in **1970**, and it is based on **set theory** and **first-order predicate logic**. A DBMS based on this model is called a **relational DBMS (RDBMS)**; for example, MySQL, Oracle, SQL Server, PostgreSQL and IBM DB2.

### Terms of the Relational Model

1. **Relation** — a table with rows and columns; for example, STUDENT.
2. **Tuple** — a row (record) of a relation; it describes one entity, for example (101, Rahim, CSE, 3.75).
3. **Attribute** — a column (field) of a relation; for example, Roll_No, Name.
4. **Domain** — the set of allowed (atomic) values of an attribute; for example, the domain of CGPA is real numbers from 0.00 to 4.00.
5. **Degree (arity)** — the **number of attributes (columns)** in a relation.
6. **Cardinality** — the **number of tuples (rows)** in a relation.
7. **Relation schema** — the name of a relation with its list of attributes, written R(A₁, A₂, …, Aₙ); for example, STUDENT(Roll_No, Name, Dept, CGPA). It is the design and changes rarely.
8. **Relation instance (relation state)** — the set of tuples in a relation at a particular moment; it changes with every insert, update and delete.
9. **Relational database schema** — the set of all relation schemas of a database together with its integrity constraints.
10. **NULL** — a special marker for a value that is **unknown, missing or not applicable**; it is not the same as zero or a blank space.

In the STUDENT relation above, the degree is **4** (Roll_No, Name, Dept, CGPA) and the cardinality is **4** (four students).

### Properties of a Relation

1. Each relation has a **distinct name** in the database.
2. Each cell contains a **single, atomic value** (no lists or repeating groups).
3. Each attribute has a **distinct name**.
4. All values of an attribute come from the **same domain**.
5. **No two tuples are identical** (each row is unique).
6. The **order of tuples** does not matter.
7. The **order of attributes** does not matter.

### Keys in the Relational Model

A key is an attribute or a set of attributes that **uniquely identifies each tuple** in a relation and is used to relate tables.

1. **Super key** — any set of one or more attributes that uniquely identifies a tuple; it may contain extra attributes. Example: {Roll_No}, {Roll_No, Name}.
2. **Candidate key** — a **minimal super key**: no attribute can be removed from it without losing uniqueness. A relation may have several. Example: Roll_No, NID_No, Email.
3. **Primary key** — the candidate key **chosen** to identify the tuples of a relation; its values must be **unique and never NULL**. A relation has only one primary key. Example: Roll_No.
4. **Alternate key** — a candidate key that is **not chosen** as the primary key. Example: NID_No and Email when Roll_No is the primary key.
5. **Composite key** — a key made of **two or more attributes**. Example: {Roll_No, Course_ID} in ENROLLMENT.
6. **Foreign key** — an attribute (or set) in one relation that **refers to the primary key of another relation**; it links the two relations. It can repeat and can be NULL. Example: Dept_ID in STUDENT refers to Dept_ID in DEPARTMENT.
7. **Unique key** — an attribute whose values must be unique, but which (unlike a primary key) may contain NULL. Example: Email.
8. **Surrogate key** — an **artificial key** generated by the system (for example, an auto-increment number) that has no business meaning, used when no suitable natural key exists.

Relationship among keys: every primary key and alternate key is a candidate key, and every candidate key is a super key.

### Codd's 12 Rules

In 1985 Codd published rules that a DBMS must satisfy to be called fully relational. With the foundation rule (Rule 0) they are thirteen, but they are known as **Codd's 12 rules**:

0. **Foundation rule** — the system must manage its databases entirely through its relational capabilities.
1. **Information rule** — all data, including metadata, is stored as values in cells of tables.
2. **Guaranteed access rule** — every value can be reached by **table name + primary key value + column name**.
3. **Systematic treatment of NULL values** — NULL represents missing or inapplicable data, uniformly.
4. **Active online catalog** — the structure of the database (data dictionary) is stored in tables and can be queried by authorized users with the same language.
5. **Comprehensive data sub-language** — one language (such as SQL) must support data definition, manipulation, integrity, authorization and transactions.
6. **View updating rule** — all views that are theoretically updatable must be updatable by the system.
7. **High-level insert, update and delete** — these operations work on **sets of rows**, not only one row at a time.
8. **Physical data independence** — changes in physical storage do not affect application programs.
9. **Logical data independence** — changes in the logical structure (for example, splitting a table) do not affect application programs.
10. **Integrity independence** — integrity constraints are defined in the catalog, not in application programs.
11. **Distribution independence** — users need not know whether the data is distributed across sites.
12. **Non-subversion rule** — low-level access must not bypass the integrity and security rules.

### DBMS vs RDBMS

| Basis | DBMS | RDBMS |
| --- | --- | --- |
| Data storage | As files, or in a hierarchical or network form | As related tables (relations) |
| Relationships | Few or none between data items | Tables related through keys |
| Normalization | Not applicable | Tables are normalized to reduce redundancy |
| Integrity constraints | Limited | Primary key, foreign key and other constraints enforced |
| Codd's rules | Not followed | Follows Codd's rules |
| Users and data | Usually small data, fewer users | Large data, many concurrent users |
| Distributed databases | Usually not supported | Supported |
| Hardware and cost | Lower | Higher |
| Examples | File systems with XML, dBase, early hierarchical/network systems | MySQL, Oracle, SQL Server, PostgreSQL, DB2 |

### Advantages of the Relational Model

1. **Simple** — data is shown as easy-to-understand tables.
2. **Structural independence** — the structure can change without affecting data access.
3. **Powerful query language (SQL)** — data is retrieved without writing procedures.
4. **Data integrity** — keys and constraints keep data accurate.
5. **Flexible** — tables can be combined in many ways with joins.
6. **Sound mathematical foundation** (set theory and relational algebra).

### Disadvantages of the Relational Model

1. **Performance** — joins over very large tables can be slow and need powerful hardware.
2. **Complex data** — images, nested and hierarchical data do not fit naturally into flat tables.
3. **Normalization overhead** — splitting data into many tables requires many joins.

### Relational Algebra

Relational algebra is a **procedural query language** consisting of a set of operations that take one or two relations as input and produce a new relation as output.

It is the theoretical basis of SQL.

#### Fundamental Operations

1. **Selection (σ)** — a unary operation that selects the **rows** satisfying a condition, written as **σ condition (R)**. Example: σ Dept = 'CSE' (STUDENT) returns Rahim and Sumi.
2. **Projection (π)** — a unary operation that selects the **columns** named and removes duplicate rows: **π attribute-list (R)**. Example: π Name, Dept (STUDENT).
3. **Union (∪)** — R ∪ S contains the tuples that are in R, in S, or in both (duplicates removed). R and S must be **union-compatible**: the same number of attributes with matching domains.
4. **Set difference (−)** — R − S contains the tuples that are in R but not in S.
5. **Cartesian product (×)** — R × S combines **every tuple of R with every tuple of S**; if R has m tuples and S has n tuples, the result has **m × n** tuples, and its degree is the sum of the two degrees.
6. **Rename (ρ)** — gives a new name to a relation or to its attributes: ρ X (R).

#### Additional Operations

1. **Intersection (∩)** — R ∩ S contains the tuples that are in both R and S; R ∩ S = R − (R − S).
2. **Join (⋈)** — combines related tuples of two relations: R ⋈ condition S = σ condition (R × S).
   - **Theta join** — join with any comparison condition (<, >, =, ≤, ≥, ≠).
   - **Equi-join** — a theta join with only equality conditions.
   - **Natural join** — an equi-join on all attributes with the same name, keeping one copy of each common attribute.
   - **Outer joins** — keep unmatched tuples too, filling the missing values with NULL: **left**, **right** and **full** outer join.
3. **Division (÷)** — R ÷ S returns the values of R that are related to **every** tuple of S; used for "all" queries.

#### Example of Relational Algebra

Let BANGLA = {Rahim, Karim, Sumi} and ENGLISH = {Sumi, Nila, Rahim} be the names of students taking two courses:

1. BANGLA ∪ ENGLISH = {Rahim, Karim, Sumi, Nila}
2. BANGLA ∩ ENGLISH = {Rahim, Sumi}
3. BANGLA − ENGLISH = {Karim}
4. If ENROL(Student, Course) = {(Rahim, C1), (Rahim, C2), (Karim, C1), (Sumi, C1), (Sumi, C2)} and COURSE = {C1, C2}, then ENROL ÷ COURSE = {Rahim, Sumi} — the students who take **all** the courses.
5. If R has 3 tuples and S has 2 tuples, R × S has 3 × 2 = **6** tuples.

**Relational calculus** is a non-procedural query language in which a query states **what** to retrieve, not how to retrieve it.

It has two forms, **tuple relational calculus**, for example { t | STUDENT(t) ∧ t.Dept = 'CSE' }, and **domain relational calculus**; both have the same expressive power as relational algebra (for safe expressions).

## Integrity Constraints {#integrity-constraints}

### Definition of Integrity Constraints

Integrity constraints are **rules defined on a database that the data must always satisfy** to keep it accurate, consistent and valid.

The DBMS checks them on every insert, update and delete, and **rejects any operation that would violate them**. They can be written with a column (column constraint) or at the end of the table definition (table constraint).

### Types of Integrity Constraints

There are four main types of integrity constraints:

1. **Domain constraint** — every value of an attribute must be an **atomic value from its domain** (correct data type, length and range). Example: Age must be a positive integer; a letter cannot be stored in an integer column. Implemented with data types, **NOT NULL** and **CHECK**.
2. **Entity integrity constraint** — the **primary key cannot be NULL**, because the primary key identifies each tuple.
3. **Key constraint (uniqueness)** — the values of a primary key or candidate key must be **unique**: no two tuples can have the same key value.
4. **Referential integrity constraint** — a **foreign key value must either match an existing primary key value in the referenced (parent) table or be NULL**. Example: every Dept_ID in STUDENT must exist in DEPARTMENT.

#### Referential Integrity Example

DEPARTMENT (referenced / parent table):

| Dept_ID | Dept_Name |
| --- | --- |
| CS | Computer Science |
| EE | Electrical Engineering |
| BA | Business Administration |

STUDENT (referencing / child table):

| Roll_No | Name | Dept_ID |
| --- | --- | --- |
| 101 | Rahim | CS |
| 102 | Karim | EE |
| 103 | Sumi | CS |

1. **Insertion:** inserting (104, Nila, ME) is **rejected**, because ME does not exist in DEPARTMENT.
2. **Deletion:** deleting department CS is **rejected** while students refer to it (unless a referential action is set); deleting BA is allowed, because no student refers to it.

#### Referential Actions

When a referenced row is deleted or updated, the DBMS can take one of these actions:

1. **ON DELETE / ON UPDATE CASCADE** — the matching rows of the child table are also deleted or updated.
2. **ON DELETE SET NULL** — the foreign key in the child rows is set to NULL.
3. **ON DELETE SET DEFAULT** — the foreign key is set to its default value.
4. **RESTRICT / NO ACTION** — the deletion or update is rejected.

### Constraints in SQL

1. **NOT NULL** — the column cannot contain NULL.
2. **UNIQUE** — all values in the column must be different.
3. **PRIMARY KEY** — NOT NULL + UNIQUE; identifies each row; one per table.
4. **FOREIGN KEY** — the value must exist in the referenced primary (or unique) key.
5. **CHECK** — every value must satisfy a condition.
6. **DEFAULT** — gives a value to a column when no value is supplied.

```sql
CREATE TABLE Department (
    dept_id   CHAR(2)     PRIMARY KEY,
    dept_name VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE Student (
    roll_no  INT          PRIMARY KEY,
    name     VARCHAR(50)  NOT NULL,
    email    VARCHAR(60)  UNIQUE,
    cgpa     DECIMAL(3,2) CHECK (cgpa BETWEEN 0 AND 4),
    country  VARCHAR(20)  DEFAULT 'Bangladesh',
    dept_id  CHAR(2),
    FOREIGN KEY (dept_id) REFERENCES Department(dept_id) ON DELETE SET NULL
);
```

#### Primary Key vs Unique Key vs Foreign Key

| Basis | Primary key | Unique key | Foreign key |
| --- | --- | --- | --- |
| Purpose | Identifies each row | Prevents duplicate values | Links to another table |
| Duplicate values | Not allowed | Not allowed | Allowed |
| NULL | Not allowed | Allowed | Allowed |
| Number per table | Only one | Many | Many |
| Refers to | — | — | Primary (or unique) key of another table |

## Transforming an ER Diagram into a Relational Model {#transforming-an-er-diagram-into-a-relational-model}

An ER diagram is converted (mapped) into relational tables by the following rules.

### Mapping Rules

1. **Strong entity** — make a **table** for each strong entity; its simple attributes become columns, and its key attribute becomes the **primary key**.
   STUDENT(**Roll_No**, Name, Date_of_Birth) — the primary key is shown in bold (underlined in diagrams).
2. **Composite attribute** — store only its **component (simple) attributes** as columns. Address(Street, City, Post_Code) → columns Street, City, Post_Code.
3. **Multivalued attribute** — make a **separate table** containing the multivalued attribute and the **primary key of the entity** as a foreign key; the primary key of the new table is the **combination of both**. STUDENT_PHONE(Roll_No, Phone) with key (Roll_No, Phone).
4. **Derived attribute** — **not stored**; it is calculated when needed (Age from Date_of_Birth).
5. **Weak entity** — make a table that includes its own attributes and the **primary key of its owner entity** as a foreign key; its primary key is **owner's primary key + partial key**. GUARDIAN(Roll_No, G_Name, Relation, Phone) with key (Roll_No, G_Name).
6. **1:1 relationship** — add the primary key of one entity as a **foreign key** in the other (preferably in the entity with **total participation**, to avoid NULLs) and make it unique; if both participations are total, the two entities may be merged into one table.
7. **1:N relationship** — add the primary key of the **"one" side** as a **foreign key** in the table of the **"many" side**; the relationship's attributes also go to the "many" side. Example: DEPARTMENT 1:N EMPLOYEE → EMPLOYEE(Emp_ID, Name, Dept_ID).
8. **M:N relationship** — make a **new table** (junction table) for the relationship, containing the **primary keys of both entities as foreign keys** plus the relationship's attributes; its primary key is the **combination of the two foreign keys**. Example: STUDENT M:N COURSE through ENROLS → ENROLS(Roll_No, Course_ID, Grade) with key (Roll_No, Course_ID).
9. **N-ary relationship** (degree > 2) — make a new table containing the primary keys of **all participating entities** as foreign keys and the relationship's attributes; the primary key is normally the combination of these foreign keys.
10. **Recursive (unary) relationship** — for 1:N, add a foreign key in the same table that refers to its own primary key: EMPLOYEE(Emp_ID, Name, Supervisor_ID), where Supervisor_ID refers to Emp_ID; for M:N, make a separate table with two foreign keys to the same table.
11. **Generalization / specialization** — usually make a table for the **superclass** with the common attributes, and a table for each **subclass** with its own attributes plus the superclass's primary key (which is both its primary key and a foreign key). Alternatively, if the specialization is total, make tables only for the subclasses, each with all inherited attributes, or put everything in one table with a type column.
12. **Aggregation** — make a table for the aggregated relationship (as for any relationship), then treat its primary key as the key of an entity in the higher-level relationship.

### Example of Mapping

ER diagram: STUDENT (Roll_No, Name, Phone [multivalued], Date_of_Birth, Age [derived]) **enrols in** COURSE (Course_ID, Title) — M:N with the attribute Grade; weak entity GUARDIAN (G_Name, Relation) identified through STUDENT.

Resulting tables:

1. STUDENT(**Roll_No**, Name, Date_of_Birth) — Age is not stored.
2. STUDENT_PHONE(**Roll_No, Phone**) — Roll_No references STUDENT.
3. COURSE(**Course_ID**, Title)
4. ENROLS(**Roll_No, Course_ID**, Grade) — both are foreign keys.
5. GUARDIAN(**Roll_No, G_Name**, Relation) — Roll_No references STUDENT.

(Primary keys are shown in bold.)
