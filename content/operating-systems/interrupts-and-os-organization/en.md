## Interrupt Processing {#interrupt-processing}

### Definition

> **An interrupt is a signal from hardware or software that tells the processor that an event needs immediate attention.**

The processor suspends the current program, runs a routine that services the event, and then resumes the interrupted program.

The routine that services an interrupt is called the **Interrupt Service Routine (ISR)** or **interrupt handler**. Hardware devices raise interrupts on an **Interrupt Request line (IRQ)**.

Without interrupts, the CPU would have to keep checking every device to see whether it needs service (**polling**), which wastes CPU time. With interrupts, the CPU does other work and the device tells the CPU when it is ready.

### Types of Interrupts

1. **Hardware interrupts:** generated by external devices (keyboard, mouse, disk, timer) or by hardware circuits. They are **asynchronous** — they can occur at any time.
   1. **Maskable interrupts:** the CPU can disable (mask) them temporarily through an interrupt mask register, for example while it handles a more important task.
   2. **Non-maskable interrupts (NMI):** cannot be disabled; used for critical events such as hardware failure or a watchdog-timer timeout.
   3. **Spurious interrupts:** hardware interrupts that have no identifiable source.
2. **Software interrupts:** generated by a program.
   1. **Normal software interrupts:** caused by special instructions, for example a **system call** (such as `fork()`), which switches the CPU from user mode to kernel mode.
   2. **Exceptions (traps):** caused by errors during execution, such as division by zero or an invalid memory access. They are **synchronous** — they occur at the same point each time the program runs.

Interrupts can also be classified by how the ISR is found:

1. **Vectored interrupts:** the interrupting device sends a code (vector) that identifies the ISR directly — faster.
2. **Non-vectored interrupts:** the CPU must find the ISR itself (for example, from a fixed location or by polling) — slower.

### Steps of Interrupt Processing

1. A device (or program) raises an interrupt.
2. The processor **finishes the current instruction**.
3. The processor **saves the state** of the running program — the program counter, registers and status word — so that it can be resumed later.
4. The CPU switches to **kernel (supervisor) mode**.
5. The processor identifies the interrupt and finds the address of its ISR using the **interrupt vector table**, and loads that address into the program counter.
6. The **ISR runs** and services the device (for example, it reads the data from the device and tells the device to remove its interrupt request).
7. The **saved state is restored**.
8. Control returns to the interrupted program (or the scheduler may choose another process to run — see [Dispatcher](#dispatcher)).

### Interrupt Vector Table

The **interrupt vector table** is a table of pointers (addresses) to the interrupt service routines.

The **interrupt vector** (the IRQ number for a hardware interrupt, or the argument of the interrupt instruction for a software interrupt) is used as an index into this table. The OS sets up the table at boot time.

### Handling Multiple Interrupts (Priority)

When several devices request service at the same time:

1. **Polling:** the processor checks the IRQ bit of each device in a fixed order and services the first one that is set. Simple, but slow.
2. **Vectored interrupts:** each device identifies itself, so the processor does not have to search.
3. **Interrupt nesting (priority interrupts):** each device has a priority. While an interrupt is being serviced, only requests of **higher priority** are accepted; lower-priority requests wait. The current priority level is kept in the processor status register.

### Interrupt Latency

**Interrupt latency** is the delay between the moment an interrupt is generated and the moment its ISR starts executing.

It depends on the number of enabled interrupts, the time needed to save the registers, and the time spent in other ISRs.

### Interrupt vs Polling

| Basis | Interrupt | Polling |
| --- | --- | --- |
| Who starts it | The device signals the CPU when it needs service | The CPU checks each device repeatedly |
| CPU time | Not wasted; the CPU does other work | Wasted checking devices that are not ready |
| Response | Fast, as soon as the event happens | Depends on how often the CPU checks |
| Hardware | Needs interrupt-handling hardware | Simple |

### Advantages and Disadvantages of Interrupts

- **Advantages:** no CPU time is wasted on polling; fast response to events; computation and I/O overlap; supports multitasking.
- **Disadvantages:** needs interrupt hardware; the design of ISRs is complex; very frequent interrupts add overhead.

## Operating System Organization {#operating-system-organization}

The **structure (organization) of an operating system** is the way its components are arranged and connected to one another and to the hardware.

The main structures are:

1. Simple structure
2. Monolithic structure
3. Layered structure
4. Microkernel structure
5. Modular structure
6. Hybrid structure
7. Exokernel structure
8. Virtual machine structure

### 1. Simple Structure

There is no well-defined structure; the interfaces and levels of functionality are not separated, and application programs can access the basic I/O routines and hardware directly.

- **Example:** MS-DOS.
- **Advantages:** easy to develop; good performance, because there are few layers between the application and the hardware.
- **Disadvantages:** not protected or reliable — a failure in one user program can crash the whole system; hard to maintain and change.

### 2. Monolithic Structure

The **whole operating system runs as one large program in kernel mode**. All services — process management, memory management, file system and device drivers — are inside a single kernel and share one address space. Applications request services through system calls.

- **Examples:** UNIX, Linux, OS/360.
- **Advantages:** fast, because components call each other directly without message passing; simple to design.
- **Disadvantages:** a bug in any part can crash the whole system; difficult to add or change services; large and hard to maintain.

### 3. Layered Structure

The OS is divided into a number of **layers (levels)**. The bottom layer (layer 0) is the **hardware** and the top layer is the **user interface**. Each layer uses only the services of the layer **below** it and provides services to the layer above.

- **Examples:** THE operating system, MULTICS, UNIX (in a simple form).
- **Advantages:** easy to debug and verify — each layer is tested before the next is added; a layer can be changed without affecting the others; information hiding.
- **Disadvantages:** slower, because a request may pass through many layers; the layers must be carefully planned, since a layer can use only lower layers.

### 4. Microkernel Structure

Only the most essential functions are kept in the kernel — **low-level memory management, interprocess communication (IPC) and basic scheduling**. Other services (device drivers, file systems, networking) run as **user-level server processes**. Applications and servers communicate by **message passing** through the microkernel.

- **Examples:** Mach, MINIX 3, L4.
- **Advantages:** reliable and secure — a failed service does not crash the kernel; easy to extend (new services are added without changing the kernel); the small kernel is easy to port.
- **Disadvantages:** slower, because of message passing and frequent user–kernel mode switches; harder to design.

### 5. Modular Structure

The kernel has a small set of core components, and other services are **loadable kernel modules**, added at boot time or while the system runs. Each module has a defined interface, and any module can call any other module.

- **Examples:** Solaris, Linux (loadable kernel modules).
- **Advantages:** flexible and customizable; new features can be added without rebuilding the kernel; faster than a microkernel, because modules do not need message passing.

### 6. Hybrid Structure

A **hybrid kernel** combines the monolithic and microkernel approaches: some services run in the kernel for speed, while others are kept separate for modularity and reliability.

- **Examples:** Windows NT family (Windows 2000, XP, 10, 11), macOS (XNU kernel).

### 7. Exokernel Structure

Developed at **MIT**, the exokernel is a very small kernel that only **protects** hardware resources and leaves their **management** to the applications. Applications build their own abstractions through library operating systems.

- **Advantages:** high performance and flexibility, because applications control the resources.
- **Disadvantages:** complex design; less safe if applications are badly written.

### 8. Virtual Machine Structure

The hardware (CPU, memory, disks, network) is abstracted so that **several virtual machines** run on one physical machine. Each virtual machine behaves like a separate computer and can run its own operating system.

- **Examples:** VirtualBox, VMware, IBM VM/370.
- **Advantages:** complete isolation between machines; several operating systems run on one computer; useful for testing.
- **Disadvantages:** lower performance than real hardware; uses a lot of resources; complex to implement.

![Layered structure, monolithic kernel and microkernel compared](/diagrams/operating-systems/os-structures.svg)

### Monolithic Kernel vs Microkernel

| Basis | Monolithic kernel | Microkernel |
| --- | --- | --- |
| Services | All OS services run in kernel space | Only essential services in kernel; others in user space |
| Address space | One address space for all services | User services and kernel in separate address spaces |
| Size | Large | Small |
| Speed | Faster | Slower (message passing) |
| Communication | Direct function calls | Message passing (IPC) |
| Effect of a failure | Can crash the whole system | Usually limited to that service |
| Adding new services | Difficult | Easy |
| Examples | UNIX, Linux | Mach, MINIX 3, L4 |

## OS Kernel {#os-kernel}

### Definition

> **The kernel is the core part of the operating system that manages the CPU, memory and devices and acts as the bridge between application software and the hardware.**

It is loaded first when the computer starts and stays in main memory until the system shuts down.

Applications cannot use the hardware directly; they send requests to the kernel through **system calls**, and the kernel carries them out in **kernel mode**.

### Functions of the Kernel

1. **Process management:** creating, scheduling and terminating processes; context switching.
2. **Memory management:** allocating and freeing memory; giving each process its own address space; virtual memory.
3. **Device management:** controlling I/O devices through device drivers.
4. **File system management:** file operations and the file-system interface.
5. **Interrupt handling:** responding to hardware and software interrupts.
6. **Interprocess communication and synchronization.**
7. **Security and protection:** enforcing access control.

### Types of Kernel

| Type | Idea | Examples |
| --- | --- | --- |
| Monolithic kernel | All OS services in one kernel, in kernel space | UNIX, Linux, OpenVMS |
| Microkernel | Minimal kernel; most services in user space | Mach, MINIX 3, L4 |
| Hybrid kernel | Mix of monolithic and microkernel | Windows NT family, macOS (XNU) |
| Nanokernel | Extremely small kernel providing only hardware abstraction | EROS |
| Exokernel | Only protects resources; applications manage them | MIT Exokernel (Aegis, XOK) |

### Kernel vs Shell

| Basis | Kernel | Shell |
| --- | --- | --- |
| Role | Core of the OS; manages hardware and resources | Interface between the user and the kernel |
| Interaction | Users do not interact with it directly | Users type commands in it (CLI) or use a GUI |
| Function | Executes system calls | Interprets commands and calls system programs |
| Examples | Linux kernel, Windows NT kernel | Bash, C-Shell, Command Prompt |

## FLIH (First-Level Interrupt Handler) {#flih-first-level-interrupt-handler}

### Definition

> **The First-Level Interrupt Handler (FLIH) is the part of the operating system that receives control first when an interrupt occurs.**

It saves the state of the interrupted program, finds the source of the interrupt, and passes control to the routine that services that interrupt.

In modern operating systems, interrupt handling is split into two levels:

1. **First-Level Interrupt Handler (FLIH)** — also called the **hard** or **fast** interrupt handler (the **top half** in Linux).
2. **Second-Level Interrupt Handler (SLIH)** — also called the **soft** or **slow** interrupt handler (the **bottom half** in Linux; **Deferred Procedure Calls** in Windows).

### Functions of the FLIH

1. **Saves the volatile environment** (program counter, registers, status) of the interrupted process.
2. **Identifies the source** of the interrupt — by examining the interrupt vector, or by polling the devices in order of priority.
3. **Masks** other interrupts of equal or lower priority for a short time.
4. Performs the urgent, **device-specific** work quickly — for example, records information that is available only at the time of the interrupt.
5. **Passes control** to the appropriate interrupt service routine or **schedules the SLIH** for the longer processing.

### Functions of the SLIH

The SLIH completes the long interrupt-processing work. It runs more like a normal process (in its own kernel thread or a pool of kernel threads), with interrupts enabled.

### Why Interrupt Handling Is Split into Two Levels

1. While the FLIH runs, other interrupts are masked, so a long FLIH could make the system **lose interrupts**.
2. A long FLIH causes **jitter** (unpredictable delays) in the execution of processes, which is harmful in real-time systems.
3. So the FLIH is kept **as short as possible**, and as much work as possible is moved to the SLIH.

| Basis | FLIH | SLIH |
| --- | --- | --- |
| Other names | Hard / fast interrupt handler; top half | Soft / slow interrupt handler; bottom half |
| Runs | Immediately when the interrupt occurs | Later, when scheduled |
| Interrupts | Masked (equal and lower priority) | Enabled |
| Work | Short, urgent, device-specific | Long, deferred processing |
| Jitter | Causes more jitter | Causes less jitter |

## Dispatcher {#dispatcher}

### Definition

> **The dispatcher is the module of the operating system that gives control of the CPU to the process selected by the short-term (CPU) scheduler.**

The scheduler **decides** which process should run next; the dispatcher **carries out** that decision. The dispatcher runs on every process switch, so it must be very fast.

### Functions of the Dispatcher

1. **Context switching:** saving the state of the old process in its PCB and loading the saved state of the new process from its PCB.
2. **Switching to user mode.**
3. **Jumping to the proper location** in the user program (loading the program counter) to restart that program.

### Dispatch Latency

> **Dispatch latency is the time the dispatcher takes to stop one process and start another.**

Dispatch latency is pure overhead, so it should be as small as possible.

### Example

Suppose P1, P2, P3 and P4 arrive in the ready queue in that order and the system uses FCFS scheduling:

1. The scheduler selects P1, because it arrived first.
2. The dispatcher gives the CPU to P1 (context switch, user mode, jump to P1's next instruction).
3. When P1 leaves the CPU, the scheduler selects P2 and the dispatcher gives P2 the CPU.
4. The same continues for P3 and P4.

### Scheduler vs Dispatcher

| Basis | Scheduler | Dispatcher |
| --- | --- | --- |
| Role | Selects the process to run next | Gives the CPU to the selected process |
| Types | Long-term, medium-term and short-term | No types; a single module |
| Algorithm | Uses scheduling algorithms (FCFS, SJF, Round Robin, Priority) | Uses no algorithm |
| Dependency | Works independently | Works only after the scheduler's decision |
| Work done | Process selection and queue management | Context switch, switch to user mode, jump to the program location |
| Time | Takes longer to decide | Very short (dispatch latency) |

## Interrupts and Traps {#interrupts-and-traps}

### Definitions

**An interrupt** is a signal, usually from a hardware device, that needs the CPU's immediate attention: the CPU suspends the running program, runs an interrupt service routine (ISR) and then resumes the program.

**A trap** is a software-generated interrupt caused either by an error in the running program or by a deliberate request from the program for an operating-system service (a system call).

A trap is also called a **software interrupt** or an **exception**. The types of interrupts (hardware and software, maskable and non-maskable, vectored and non-vectored) are explained in [Interrupt Processing](#interrupt-processing).

**Note:** the pin named **TRAP** on the 8085 microprocessor is a non-maskable **hardware** interrupt; it is not a trap in the operating-system sense.

### Internal and External Interrupts

1. **External interrupts:** come from outside the program — from I/O devices (a request or the completion of a transfer), timing devices (a timer runs out, for example when a program is in an endless loop) or other external events such as a power failure. They are **asynchronous**: they do not depend on the instruction being executed.
2. **Internal interrupts (traps):** come from the program itself, through an illegal or erroneous use of an instruction or of data — for example register overflow, division by zero, an invalid opcode, stack overflow or a protection violation. They are **synchronous**: if the program is run again with the same data, the interrupt occurs at the same place.

### Causes of Traps

1. **Division by zero.**
2. **Invalid memory access** (protection violation, segmentation fault).
3. **Page fault** (the referenced page is not in main memory — see [Page Fault Handling](/topics/operating-systems/virtual-memory#page-fault-handling)).
4. **Illegal or invalid instruction** (an opcode that does not exist).
5. **Attempt to execute a privileged instruction in user mode.**
6. **Overflow** (arithmetic overflow, stack overflow).
7. **Breakpoint**, used by debuggers.
8. **System call:** a deliberate request for an operating-system service, such as reading a file, allocating memory or creating a process.

### How an Interrupt Is Handled

1. A device raises an interrupt request.
2. The CPU finishes the current instruction and checks for pending interrupts.
3. The CPU saves the context (program counter and registers) of the running program.
4. The CPU switches to kernel mode and identifies the source of the interrupt — through the interrupt vector table (vectored interrupts) or by polling.
5. Control passes to the interrupt service routine (ISR), which services the device.
6. The saved context is restored, and the interrupted program continues from the next instruction.

### How a Trap Is Handled

1. An error occurs, or the program executes a trap (system-call) instruction. For a system call, the program first puts the service number and its arguments in registers.
2. The CPU saves the state of the program and switches from **user mode to kernel mode**; control goes to the trap handler through the vector (dispatch) table.
3. The handler finds the cause:
   1. For a **system call**, it runs the requested kernel service.
   2. For an **error** (such as division by zero or an illegal memory access), it handles the error or terminates the program.
   3. For a **page fault**, it loads the missing page.
4. If the program is not terminated, its state is restored and the CPU returns to user mode. After a system call, execution continues after the trap instruction; after a page fault, the instruction that caused the fault is executed again.

### Differences Between an Interrupt and a Trap

| Basis | Interrupt | Trap |
| --- | --- | --- |
| Generated by | Hardware devices (external events) | Software — the running program (an error or a request) |
| Other name | Hardware interrupt | Software interrupt; exception |
| Timing | Asynchronous: can occur at any time, independent of the current instruction | Synchronous: caused by a particular instruction; occurs at the same point if the program is run again |
| Purpose | Signal an external event, such as the completion of I/O | Report an error or request an operating-system service |
| Examples | Keyboard, mouse, timer, disk I/O completion, network packet | Division by zero, invalid memory access, page fault, illegal instruction, system call |
| Masking | Can be maskable or non-maskable | Cannot be masked (disabled) |
| Handler | Interrupt service routine (ISR) | Trap (exception) handler or system-call handler |
| Relationship | Not every interrupt is a trap | Every trap is a (software) interrupt |
