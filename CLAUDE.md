## 1. Project Overview

Build and maintain a public educational website for IT and Computer Science study notes, primarily targeting government IT job examinations in Bangladesh. The website works like a public study notebook.

The website will provide structured, comprehensive, exam-oriented study materials.

The content will be based on the topics in `TOPICS.md`, researched using the reference websites in `REFERENCES.md` and any additional URLs supplied by the project owner.

The website interface (navigation, headers, labels, buttons) is in English only. Topic notes are written in two languages:

- English
- Bengali (বাংলা)

The website should be useful for both learning concepts in depth and quick examination revision.

## 2. Core Objectives

1. Build a modern, responsive, user-friendly educational website.
2. Organize IT and Computer Science topics into categories and subtopics.
3. Provide topic notes in both English and Bengali.
4. Research topics using the reference websites in `REFERENCES.md`.
5. Produce accurate, well-structured, textbook-style notes.
6. Make notes easy to read, understand, search, and revise.
7. Keep the content separate from application logic.
8. Avoid unnecessary backend infrastructure.

- Prefer standard technical terminology.
- Explain concepts in a textbook-style format.

Bengali content:

- Use natural, grammatically correct Bengali.
- Explain technical concepts clearly.

- Include the English technical term alongside its Bengali explanation where appropriate.

English:

Both versions must communicate the same technical concepts and facts.

Do not mark a topic as complete until both language versions are available.

## 5. Content Research Workflow

The project owner will provide:

1. One topic at a time from `TOPICS.md`. Do not start other topics until the project owner asks.
2. Additional reference URLs, when needed (the websites in `REFERENCES.md` are always the primary sources).
3. Additional instructions when necessary.

For every topic, follow this workflow.

### Step 1: Understand the Topic

- Understand the complete scope of the requested topic.
- Identify its major concepts and subtopics.
- Determine which concepts are important for IT job examinations.
- Prepare a logical outline before writing.

### Step 2: Research Reference Sources

**Source priority rule (from the project owner):** the five reference websites in `REFERENCES.md` (IT Job QnS, TutorialsPoint, GeeksforGeeks, TpointTech, Programiz) always have priority.

1. **Check every subtopic on the reference websites first.** For each subtopic, definition and comparison ("difference between …") table, search all five reference websites for that exact item and read the matching pages before writing anything. Prepare the answer only after this check.
2. **Build the answer from the reference websites.** Use their points, classifications and comparison tables as the basis of the notes, written in original wording. Do not leave out a point they give, and do not drop a point as "unsourced" without checking them.
3. **If one reference website has an issue, cross-check the others first.** When a reference website has an error, a contradiction, or an unclear or incomplete answer, check the same item on **all the other reference websites**.
4. **Go to other sites only when needed.** Use another source (official documentation, standards, textbooks, established encyclopedias) **only** when:
   1. the reference websites do not cover the item, or
   2. after cross-checking all the reference websites, an issue or any confusion remains (they disagree, all are unclear, or the answer still looks wrong). Cite the source used.
5. **If the reference websites answer the item correctly and agree, do not visit other sites for it.**
6. **Accuracy first.** The notes are used for examination preparation, so any wrong information costs the reader. Never publish a point you are not sure of; resolve every doubt with the steps above, and report any point that remains uncertain to the project owner.

**How to check the five websites (mandatory for every topic):**

1. **Search each website separately**, one search per website (for example, a web search limited to that one domain). Never rely on a single combined search ("site A OR site B"); it silently misses pages.
2. **Do not give up after one failed attempt.** If a guessed URL returns 404, search that website for the correct page. If a page is cut off (long menus can fill the first part of a fetched page), read the rest of it.
3. **Keep a checklist** for the topic: every subtopic and comparison table × the five websites, each cell recording the page that was read or "this website has no page on it". Write the notes only when every cell is filled.
4. **Write the best answer:** combine the points, classifications, examples and table rows of all five websites into one complete, correct answer.
5. **Report** to the project owner which websites had no page for an item, and every issue found on a website and how it was resolved.

Also:

- Visit any additional URLs provided by the project owner.
- Extract relevant information from accessible sources.
- Compare information from the reference websites.
- Verify technical definitions, facts, examples, and explanations.
- Identify outdated or conflicting information.
- Never invent facts, references, statistics, or technical details.

If a reference URL cannot be accessed, report the problem instead of pretending it was researched.

### Step 3: Prepare Structured Notes

Create comprehensive notes using the content standards defined in this file.

Do not blindly copy paragraphs from reference websites.

Understand the source material and explain it in original wording.

### Step 4: Prepare Both Languages

Create the English and Bengali versions.

Ensure:

- Technical accuracy in both languages.
- Equivalent coverage of important concepts.
- Consistent terminology.
- Natural language and readable explanations.

### Step 5: Save and Validate

- Save the notes in the appropriate content directory.
- Validate the Markdown and frontmatter against the format in section 7.
- Check internal links.
- Check references.
- Verify that both languages are available.
- Ensure the website renders the new content correctly.

## 6. Note Writing Standards

Notes must be comprehensive, educational, and examination-oriented.

**Scope rule (from the project owner):** the reader must learn and memorise every topic to write it in the examination, so notes cover **only** the subtopics listed for the topic in `TOPICS.md`, cross-checked on the reference sites. Do not add extra sections or background (word origins, related concepts, limitations, revision lists and so on) that the subtopic list does not name. Explain each listed subtopic fully, but do not pad it. Do not add examination questions. Take each answer from the reference sites in `REFERENCES.md`; only when they do not cover it, use another strong, reputable source (official documentation, textbooks, established encyclopedias) and cite it. The approved model is `content/computer-fundamentals/introduction-to-computers/en.md`.

**Mathematics rule (from the project owner):** whenever a topic or subtopic has a mathematical part — formulas, derivations, numerical problems, complexity calculations, recurrences, conversions and so on — include it: state the formula with every symbol explained, and work at least one complete numerical example step by step. Verify every calculation (for example, with a short script) before publishing it.

**List rule (from the project owner):** whenever an answer names several items (units, types, examples, uses, devices and so on), write them as a **numbered list**, one item per line, not as a comma-separated sentence. For example, "five functional units: Input Unit, Memory Unit, …" becomes `1. Input Unit`, `2. Memory Unit`, and so on.

Use the following structure when relevant:

1. Introduction
2. Definition
3. Explanation
4. Characteristics
5. Components
6. Types or Classification
7. Working Principles
8. Advantages
9. Disadvantages
10. Applications
11. Examples
12. Comparison Tables
13. Important Facts

Not every topic requires every section. Use only relevant sections.

Topic notes do not contain examination questions. Questions belong to the separate Previous Questions and MCQs sections of the website (see section 9).

### Explanation Quality

- Explain concepts in sufficient detail.
- Do not write overly short or superficial notes.
- Avoid unnecessary repetition.
- Explain technical terms when they first appear.
- Use practical examples wherever helpful.
- Include step-by-step explanations for complex concepts.
- Use comparison tables when comparing related concepts.
- Use diagrams when they improve understanding.

### Examination-Oriented Content

Give special attention to:

- Important definitions.
- Key characteristics.
- Differences between similar concepts.
- Technical terminology.
- Classifications and categories.
- Important years, inventors, and historical developments when relevant.
- Formulas and numerical examples.
- Commonly tested facts.
- Conceptual and analytical questions.

Do not invent claims about what frequently appears in examinations without supporting evidence.

## 7. Content Organization

Organize content by category, topic, and subtopic, exactly as defined in `TOPICS.md`. Category folder names and topic slugs come from `TOPICS.md`; do not invent new ones.

Directory structure:

```text
content/
└── <category-folder>/          e.g. operating-systems/
    ├── category.json           generated from TOPICS.md (do not edit by hand)
    └── <topic-slug>/           e.g. process-management/
        ├── en.md               topic notes (English)
        └── bn.md               topic notes (Bengali, Phase 2)
```

Each topic is one page at `/topics/<category-folder>/<topic-slug>`. Each subtopic is a section inside that topic's page. Clicking a subtopic in the sidebar opens the topic page scrolled to that section.

For subjects listed under "Shared Topics" in `TOPICS.md`, write the full explanation only in the main home and link to it from the other places.

### Topic Structure: `category.json`

`category.json` holds the category title and order, and every topic with its slug, title, order, exam tags and subtopics. It is **generated** from `TOPICS.md` by:

```bash
npm run topics:sync
```

Run this command after every change to `TOPICS.md`, then rebuild. The script (`scripts/sync-topics.mjs`) only writes `category.json` files; it never touches `en.md` or `bn.md`.

```json
{
  "title": "Operating Systems",
  "order": 6,
  "topics": [
    {
      "slug": "process-management",
      "title": "Process Management",
      "order": 2,
      "exams": ["School-2", "College", "PSC-IT", "AP"],
      "subtopics": [
        { "id": "concept-of-a-process", "title": "Concept of a Process", "exams": ["School-2", "College"] }
      ]
    }
  ]
}
```

- Subtopic `id`s are generated from the subtopic titles (lowercase, words joined by hyphens). Nested items in `TOPICS.md` become a subtopic's `children`.
- Untagged subtopics inherit their topic's exam tags.

### Notes File Format: `en.md` and `bn.md`

The topic's title, order and exam tags come from `category.json`, so the notes files contain only a short frontmatter and the notes.

```markdown
---
description: Process concept, process states, PCB, process context and UNIX process control.
updated: 2026-10-31
---

## Concept of a Process {#concept-of-a-process}

...

## Process States {#process-states}

...

## References {#references}

...
```

| Field         | Required | Rule                                                                 |
| ------------- | -------- | -------------------------------------------------------------------- |
| `description` | Yes      | One sentence, used for the page meta description and topic listings. |
| `updated`     | Yes      | Date of the last content change (`YYYY-MM-DD`).                      |

**`bn.md`** — same format, with `description` in Bengali. It may also add `title` with the Bengali topic title.

### Markdown Rules

- Do not use a level-1 heading (`#`). The page title comes from `category.json`.
- Use one `##` heading per subtopic, in the same order as `category.json`, followed by `References`.
- Every subtopic `##` heading must end with its ID from `category.json`: `{#concept-of-a-process}`. The sidebar links to these IDs. `References` uses `{#references}`. The IDs in `bn.md` must be identical to those in `en.md`.
- Use `###` and lower headings for structure inside a subtopic. They do not need custom IDs.
- Use GitHub-flavored Markdown tables for comparisons.
- Link to other topics with site-relative links (for example, `/topics/operating-systems/virtual-memory#page-replacement-strategies`).
- Do not write HTML inside Markdown. Raw HTML is not rendered by the website.
- **Diagrams:** draw original SVG diagrams (do not copy images from books or websites; they are copyrighted). Put them in `public/diagrams/<category-folder>/` and use them with Markdown image syntax: `![Alt text](/diagrams/digital-logic/and-gate.svg)`. Diagrams are generated by scripts, one per category: `node scripts/draw-logic-diagrams.mjs` (digital logic), `node scripts/draw-dsa-diagrams.mjs` (data structures and algorithms), `node scripts/draw-os-diagrams.mjs` (operating systems), `node scripts/draw-se-diagrams.mjs` (software engineering), `node scripts/draw-dbms-diagrams.mjs` (database management systems), `node scripts/draw-network-diagrams.mjs` (computer networks) and `node scripts/draw-ai-diagrams.mjs` (artificial intelligence, big data and cloud computing); add new ones to the matching script. Whenever a topic has something that a figure explains better (state diagrams, Gantt charts, hardware flow, trees, layouts), add a diagram. Notes show images on a white card in both themes.
- **Definitions** are shown in a theme-coloured box (accent tint, aqua left border) automatically (`src/lib/remark-definition-boxes.ts`, styled by `.definition-box` in `src/app/globals.css`); no special markup is needed. Write each definition as its own paragraph in one of these forms so it is detected: after a `### Definition` / `### Definition of X` heading; as `**Definition:** …`; as the first paragraph after heading X that starts "X is …"; as `**X** is a/an/the …`; or as `**X:** an X is …`. A definition paragraph that ends with ":" keeps the list after it in the box.
- **Code tabs:** to show the same program in several languages with a tab for each, write the fenced code blocks one after another and add `tab` after the language (```` ```c tab ````, ```` ```python tab ````). Consecutive `tab` blocks become one tab group (`src/lib/rehype-code-tabs.ts`, styled by `.code-tabs` in `src/app/globals.css`; up to four tabs). The tab label is the language name, or the text after `tab=` (```` ```text tab=Output ````). Verify every program by compiling and running it, and show the real output.
- Supported Markdown: GitHub-flavored Markdown (tables, task lists, strikethrough, autolinks), lists, block quotes, inline code and fenced code blocks.

### Rendering and Validation

- A topic page shows its notes when `en.md` exists (`src/lib/notes.ts`); otherwise it shows the subtopic outline from `category.json`.
- `npm run build` fails, naming the file, when a notes file has: missing or invalid frontmatter (`description`, `updated` as `YYYY-MM-DD`), a level-1 heading, a `##` heading without an ID, or a `##` ID that is not one of the topic's subtopic IDs or `references`. Run the build after adding or editing notes.

### Single Source of Truth

- `TOPICS.md` is the planning document and the source of the topic structure. The website never reads it directly; `npm run topics:sync` copies its structure into `content/<category>/category.json`.
- The website builds its navigation, sidebar, pages, exam filter and language availability **only** from the `content/` folder (`src/lib/topics.ts`).
- The Bengali toggle is enabled for a topic only when its `bn.md` exists.
- When a topic's notes are added or changed, update its status in `TOPICS.md`.

## 10. UI/UX Guidelines

The website should look like a professional educational platform.

Design requirements:

- Clean and minimal interface.
- Excellent readability.
- Proper typography for both English and Bengali.
- Consistent spacing and visual hierarchy.
- Comfortable reading width.
- Responsive layouts for desktop, tablet, and mobile.
- Clear heading hierarchy.
- Attractive code blocks and tables.
- Accessible color contrast.
- Easy navigation between categories and topics.

Use appropriate Bengali fonts, such as Noto Sans Bengali.

Avoid excessive animations, unnecessary decorative elements, and distracting UI components.

The reading experience should be the primary design priority.

### Visual Style

- The home page hero has a dotted background with two soft colour glows (`src/components/hero-section.tsx`, `src/components/dot-background.tsx`). The rest of the page uses a plain background.
- **Colour palette** (from the project owner, used in both themes): deep teal `#08595a` is the brand and button colour; teal `#0397a0` is used for focus rings and large text; lilac `#cbadd1`, purple `#83749e`, aqua `#69c6ca`, sky `#57bdc8`, slate `#204d58`, olive `#7ca009`, yellow `#dbda65` and forest `#203400` are accents for decoration only (they are too light or too dark for body text). They are defined as `--brand-*` variables in `src/app/globals.css`.
- **Light theme:** deep teal `#08595a` buttons and links on a light teal-white background (`#f7fbfa`).
- **Dark theme:** aqua `#69c6ca` buttons and links (with dark teal button text) on a very dark teal-slate background (`#0d1b1e`), because deep teal is too dark to read there.
- Use the theme tokens (`bg-background`, `text-muted-foreground`, `text-primary`, and so on) instead of hard-coded colors.
- **Header and footer:** share a palette gradient with light text, defined by the `--chrome-*` variables in `src/app/globals.css`. Light theme: deep teal `#08595a` → `#06787d` → slate `#204d58` (the middle stop is a deeper teal than `#0397a0` so white text keeps 4.5:1 contrast). Dark theme: dark teal `#0a2a2c` → `#0b3b3e` → `#123a44`. Yellow (light) or aqua (dark) is used for icons and bullets only, not text. A thin lilac → teal → olive line (`src/components/brand-line.tsx`) separates them from the page.
- **Topics sidebar:** a soft lilac tint like the hero glow (`--sidebar` → `--sidebar-to` in `src/app/globals.css`).
- **Remembered preferences** (exam filter, sidebar collapsed) are applied before the first paint by the inline script in `src/components/topics/topics-preferences.tsx`, so pre-rendered pages never flash the default state. Use the same approach for future preferences that change the layout.
- Home page section cards (including Coming soon cards) use a border beam (`src/components/border-beam.tsx`): two gradients that travel around the card border, using the `--beam-1-*` and `--beam-2-*` colours.
- Design ideas may be taken from [Aceternity UI](https://ui.aceternity.com/components) and [Magic UI](https://magicui.design/docs/components). Implement them with Tailwind CSS and small components; do not add the `motion` library without approval.
- Decorative effects (border beams, spotlight cards, shiny text, fade-in) belong on landing and listing pages only. Topic reading pages stay calm: no animated backgrounds or moving elements near the text.
- Every animation must respect `prefers-reduced-motion` (use Tailwind's `motion-safe:` variant).
- Keep text contrast accessible in both themes; do not fade text with opacity.

- Follow the project owner's instructions when they override these general guidelines.

## 15. Communication

Before starting a large task:

- Explain the planned approach briefly.
- Identify missing information.
- Ask questions only when necessary.

After completing a task, report:

- What was implemented.
- Which files were created or modified.
- Which sources were consulted.
- Whether both languages were completed.
- Any limitations or unresolved issues.

Always prioritize correctness, clarity, maintainability, and a high-quality learning experience.
